# Remaining design risks and implementation checks

This review concerns the M1 design on `simplify-architecture`, not an implemented platform. Chronos-2 is now the specified projection model; no model has been downloaded or benchmarked and no accuracy results are claimed.

| Priority | Weak point | Decision / required evidence |
|---|---|---|
| High | Forecast compute is unmeasured alongside local Spark. | Keep one cached CPU model in a bounded background task in the existing speed service. Benchmark 50 games, then the complete eligible set; record latency and total memory. Forecast work must not stall ingestion. Revise resource sizing if the 15-minute cycle cannot be met. |
| High | A batch layer fed by speed-layer outputs cannot independently restore correct history. | Corrected the contract: batch aggregates and manual replay read Parquet, using shared calculations. Demonstrate recovery with speed offline and the archive intact; do not recreate historical forecasts during replay. |
| High | Historical update markers cannot be re-fetched from a latest-state API. | Corrected the backup claim: versioned daily exports preserve metadata and update history outside the PostgreSQL volume. Exercise a restore; local exports do not protect against host/disk loss or observations after the last export. |
| High | Replay ordering, mixed grains and missing values can corrupt analytics. | Corrected contracts: observation-time conditional upserts, per-kind timestamps, common hour-aligned cutoff, and coverage checks before deletion. Offline acceptance checks must cover out-of-order game/vote events, replay, the cutoff boundary and gaps. |
| Medium | Forecast storage can dominate the small Parquet estimate. | Store each 12-step curve in one row, retain curves/evaluation targets for 14 days, and size PostgreSQL indexes and model weights separately. At full coverage this is 172,800 curve rows/day. |
| Medium | Matching similarity does not establish copying or a calibrated probability. | Keep UI wording as possible counterparts. Use a held-out portion of the manual labels for precision; include rejected candidates to inspect false negatives. The creation-date rule misses repurposed universes. Changing that rule is a product decision, not part of the Chronos replacement. |
| Medium | Search and tracked-set caps bias apparent competition. | Saturation is detected matched-game count and observed players, not total competition. Show missing metric counts and matching freshness. Chart/list discovery and 10–20 search hits can miss competitors; inspect coverage in the manual review. |
| Medium | Undocumented discovery and HTML parsers are fragile; probe numbers are not guarantees. | Add offline parser assertions from the saved responses and explicit live diagnostics. Preserve probe dates/parameters when repeating volume or throttling measurements. Current probe functions only fetch/save responses; the runner should eventually return nonzero on unknown names or failures. |
| Medium | Chronos may not beat simple forecasts on viral games or short histories. | Evaluate rolling historical origins against persistence, yesterday and linear slope on the same real targets. Report per-platform MAE, sample count, forecast availability, interval coverage and runtime. Do not select models using the held-out reporting window. |

The old linear projection remains an evaluation baseline, not a hidden fallback. Missing or stale Chronos forecasts are explicit UI states. Expected-player regression remains a separate model family for activity scoring; score above one does not imply positive growth.

No extra infrastructure service or paid endpoint is required by these decisions. Package/model revisions, offline tests, recovery commands and runtime benchmarks remain implementation work because the repository currently contains documentation and API probes only.
